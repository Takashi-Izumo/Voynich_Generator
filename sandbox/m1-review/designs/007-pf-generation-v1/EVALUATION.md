日付: 2026-11-05（日本時間）。入力は報告004・提案005、実装snapshot `294a7afdc86949e4f774166c449a5415de9573c1e4e57ab6bb94032df57c1504`。本書と[設計書](DESIGN.md)は設計成果物であり、新モデルの実装・fit・生成・採点結果ではない。

## 判断

| 提案 | 評価 | 初回の比較 | 優先度 |
|---|---|---|---|
| 1: PF専用の語長・幅分布とclosing gate | 生成候補の長語不足を調べる根拠が最も強い。幅配分と語内の長さを分ける必要がある | BASE / PF_GATE / PF_GATE_LENGTH | 最優先 |
| 2: 個々の末字score成分の調整 | 小さい実装で選択側の寄与を調べられる。長語の候補不足を解消する案にはならない | BASE / PF_E_HALF / PF_E_ZERO | 独立した第2段階 |
| 3: SPACE接続をPF選択へ追加 | 接続残差を扱えるが、支持が疎で提案1とも相互作用する | BASE / PF_SPACE_HEAD。語長対はさらに別比較 | 第3段階 |

**提案1を優先する。ただし「長語を増やせば改善する」とはまだ判断しない。** BASEの初期2候補の7+率4.49%と採用後4.72%は、候補生成を調べる根拠になる。真正側24.07%は18 target面・29末尾の開発集計であり、生成確率の固定目標にはしない。

## ソースを読んで補った点

1. `generate_segment()`の末尾語は、m/rare処理後の物理幅で `w == R` を満たす。継続語は `w + 2 <= R`。したがって、残り幅を小さく使い切る生成を維持したまま、末尾だけを一律に長くする設計は成立しない。gateによる幅配分を独立に検証する。
2. 現在のFastSamplerは `seg_end=True` を渡されても、一般のPF向け `qend` を直接適用していない。`qend`を差し替えるだけの変更を、PF語長法則の実装と呼んではいけない。接続先は実際のraw語生成呼出しに置く。
3. PF末尾にはBODYだけでなくW2、少数のHEADもある。新しいPF処理の直接適用範囲と、段落末segment全体の変化がHEAD/W2へ及ぼす波及を区別する。植物後segmentは引き続きBODY。
4. `LinearSelector.score()`は個別末字 `E=` と族 `EF=` を別に持つ。提案2では `E=` だけを変更できる。一方、同じscoreがLEN1の `candidate_score >= base_score - 1.0` にも使われる。LEN1の定数を保存しても、適格救済・採用・RNG継続元は変わり得る。
5. 提案005の「score全体を0.5倍してもargmaxは変わらない」はargmax単体では正しい。ただし固定値1.0の救済許容差を残すと、救済適格条件は不変ではない。score全体の縮小を無意味な恒等変換とも、個別末字だけの介入とも扱わない。
6. SPACE項は末尾語単体の既存score引数では表現できない。完成したPF候補segmentから直前語を取得する新しい選択adapterを用意する。一語segment、PLANT越え、行越えに接続を作らない。

## 設計上の選択

- 先に末尾幅を予約する方式は、継続語の幅制約や語数の経路にも変更が広がるため、初版では採らない。親gateへの少数のoffsetと、raw末尾候補への正の長さ重みを選ぶ。
- 第1案の語長法則は、親raw samplerからの支持内再標本化で実現する。語内STOP kernelの再実装を避け、親の確率行・HEAD/W2処理を保存する。有限回の打切りによるfallbackと、最終可視分布への変換を必ず測る。
- 通常行末へ縮約し、初版の縮約・重み上限・試行上限は[設計契約](DESIGN_CONTRACT.json)で固定する。これらは設計上の推奨初期値であり、最適化済みの値でもユーザー指定値でもない。
- 審判が変化を検出できるかを別の能力対照で調べる。生分布の改善だけ、CAL率の小変化だけでは採用しない。推論上の採用許容幅は今回決定しない。

既存20葉は引き続き開発資料。外側foldを守っても、これまでの全体診断を見た後の設計であることは変わらず、新しい独立確認とは呼ばない。
